# Результат, версии и общая память

## Файлы запуска

Один отчёт `reports/product-brand-identity/<timestamp>_<slug>.md`, рядом одноимённая
папка. В ней `identity.json`, masters/, exports/, previews/ и заказанные документы.
Это рекомендуемые папки, не обязательные пустые каталоги. PDF-презентация и логобук —
выходные брендовые артефакты, аналитический отчёт остаётся один. Исходники пользователя
остаются на месте; при необходимости точные копии с происхождением — в sources/.

Каждая завершённая или показанная пользователю версия неизменяема. Для продолжения
сделай новый timestamp/version и basedOn, сохрани выбранное направление и основания.
До показа можно править текущие рабочие экспорты; после изменения обновить SHA-256 и
повторить QA. При ожидании выбора сохраняй draft + waitingFor, чтобы другой агент мог
продолжить. Предлагаемые варианты ещё не отвергнуты; в IDEAS попадают только явно
отложенные решения по CONTRACT.

## identity.json

Скопируй assets/identity.template.json и заполни, не оставляй шаблон результатом.
Все `path`, `renderPath` и `basedOn.manifestFile` — относительно корня воркспейса,
не папки JSON. Выборочные примеры ниже — схема, а не данные конкретного продукта.

- `schemaVersion`: 3 для новых версий; сохранённая `presentation` описана в
  [presentation.md](presentation.md). Валидатор принимает 1, 2 и 3: для 2/3 отсутствие `check`,
  `demoFileIds`, постраничного локатора у метода и малых превью знака — ошибка, для 1
  (выпущенные ранее версии) — только предупреждение; в папки версий со схемой 1 он ничего
  не пишет.
- `product`: `{id, name}`; id существует в графе либо null при работе без графа.
- `version`: положительное целое. `basedOn`: null либо `{manifestFile, artifactId?}`;
  предыдущая версия того же продукта, без циклов, с меньшим номером.
- `scope`: logo / brand / system. `stage`: brief / directions / system / handoff.
- `readiness`: draft / ready-for-review. `decision`: proposed / accepted.
  accepted требует `decisionSource` с реальным выбором всей версии. Выбор концепции
  в `selectionSource` сам по себе не принимает ещё не показанные файлы новой системы.
- `selectedDirection`: ID выбранного направления или null. Для существующей системы
  можно записать один direction с исходными активами; повторные альтернативы не нужны.
  `selectionSource`: точный локатор выбора или поручения агенту выбрать самостоятельно.
  `waitingFor`: строка с оставшимся входом/решением или null.
- `requestedDeliverables`: заказанный поднабор brief / concepts / identity-system /
  logobook / asset-pack / applications. Не сокращать его ради зелёной проверки.
- `sources`: `{id, kind, locator, viewed, note?}`; kind: user-requirement,
  product-evidence, style-reference, existing-brand-asset, method. URL/локатор допустимы;
  копии файлов, если сделаны, регистрируются также в files. Методический источник не
  превращается в доказательство спроса, референс — в данные о продукте. Источник
  `method` указывает локатор до страницы или принципа (`…/pages/0097.txt`,
  `…ch02.xhtml#lev853`, либо «Johnson, с. 93» без базы), а не индекс базы целиком;
  индекс допустим только как отдельный источник для «прочитан синтез X». Скриншоты
  альтернатив из категории — `style-reference` с URL, датой и копией в sources/.
- `assumptions`: `{id, statement, basis, fatal, status, check?, checkResult?}`; status
  open / checked / withdrawn. При `fatal: true` поле `check` обязательно: конкретный
  дешёвый протокол с порогом, который можно выполнить за день без нового исследования —
  «показать обложку 5 секунд пяти людям из сегмента, спросить, что за компания и что
  делает; порог: 3 из 5 называют оплату подписок». `checkResult` заполняется при
  переходе в checked/withdrawn с датой и наблюдением. Число открытых/fatal выводит
  валидатор; наличие нулей не доказывает рынок. При завершении полного заказа отчёт
   выносит каждое открытое fatal-допущение в блок «Следующий дешёвый ход»: `check` как
   предложенный move (что проверяет, порог, чем закрывается) либо как задание на проверку
   людьми из сегмента (сегмент, число людей, вопрос, порог). Это предложение, не
  обязательство: в MOVES.md оно попадает через общий writer только при выборе владельца
  или в рамках уже разрешённого объёма; иначе паркуется в IDEAS.md по CONTRACT — одной
  строкой со ссылкой на отчёт и условием возврата, без копии протокола. Допущение,
  открытое три версии подряд без `check`, — дефект процесса, а не «известный риск».
- `rules`: `{id, topic, value, rationale, sourceIds, strength, scope?, exceptions?,
  demoFileIds?, pairs?}`; strength required / preferred / candidate. Прямое ограничение
  пользователя остаётся обязательным даже в предложенной версии; наблюдение чужой
  работы — не требование. У правила `required` есть `demoFileIds` — хотя бы один файл из
  `files`, где правило видно (макет, страница логобука, превью); правило без
  демонстрации — кандидат. Если `required` опирается на источник `method`, этот источник
  имеет локатор до страницы или принципа. Для `topic: color` пары «текст на фоне»
  записываются в `pairs: [{fg, bg, role, minRatio}]` в hex; валидатор печатает
  коэффициент контраста, порог `minRatio` задаёт продукт. Старые версии без этих полей
  остаются валидными; требование действует для новых версий.
- `presentation`: авторская композиция из связанных с файлами визуальных блоков.
  Для schema 3 обязательна перед `ready-for-review`; в draft допустим null.
  Порядок и набор блоков зависят от бренда; обязательные правила, источники и область
  принятия сохраняются. Консоль ничего заново не генерирует при чтении.
- `directions`: `{id, label, rationale, fileIds, tradeoffs}`. fileIds указывают на реальные
  визуалы для сравнения; selectedDirection ссылается на одну из записей.
- `files`: `{id, role, path, sha256, purpose?}`. role: source / concept-board / logo / palette /
  typography / application / presentation / logobook / delivery-index / preview.
  SHA-256 считается по фактическим байтам, например через shasum -a 256. Цифровые
  носители (иконка, favicon, аватар, og-image, письмо) — role application с `purpose`
  (`app-icon-32`, `favicon`, `avatar-round`, `og-image`, `email-header`, `dark-theme`);
  малые превью знака от валидатора — role preview в `previews/`.
- `deliverables`: `{kind, fileIds}`. Материальный результат каждого заказанного вида.
  brief может указывать на единственный отчёт, identity-system — на тот же отчёт,
  схемы и образцы; logobook — на реальный документ, asset-pack — на мастера, экспорты
  и индекс. Один источник пользователя не засчитывается как произведённый результат.
- `qa`: `{fileId, sha256, viewed, viewSize, result, issues, renderPath?}`.
  issues: `{severity: blocking|minor, detail}`. Просмотр относится к указанному хешу.
  Для PDF/PPTX список страниц/условия просмотра отражаются в result; отсутствие
  блокирующих замечаний не равно автоматическому принятию дизайна.

Перед ready-for-review все заказанные deliverables существуют; визуалы (concept-board,
logo, application, presentation и визуальный logobook) реально просмотрены, версия
QA совпадает с файлом; блокирующие вопросы отсутствуют; у каждого fatal-допущения есть
`check`; у каждого `required` — демонстрирующий файл; превью знака 16/32/64 px имеют
записи QA. Широкий поиск и таблица отброшенных идей хранятся в отчёте, не в JSON. Для system/handoff нужно
выбранное направление. Бриф и этап концепций могут быть готовы к просмотру сами по себе,
но это не завершение полного заказа с недостающими файлами. В ready-for-review для
полного заказа входят весь запрошенный комплект и проверка; само направление остаётся
proposed, если пользователь не принял результат.

## Частичный выбор и обратная связь

`decision` относится ко всей версии. При частичном выборе сохраняй в том же
identity.json `selectionHistory`: записи `{target, decision, source}` для конкретного
направления, знака или применения. `target` однозначно связан с реальными файлами
или правилами этой версии; для знака можно использовать `selectedLogo` и
`selectedLogoFiles`. `source` — точное решение владельца, а не рекомендация агента.
Не нужно добавлять пустые поля или мигрировать старые версии, где частичных решений нет.
Это поддерживающие данные: валидатор файлов не проверяет смысл и полномочия выбора.

При продолжении прочитай решения и последующие уточнения в их области, сохрани
принятые активы и отметь предложенные. Не расширяй принятие знака на всю систему,
отказ от одного применения — на сам знак, а положительный отзыв о форме — на все
её размещения. Сбой формы выбора не отменяет однозначного ответа в сообщении.

Для коррекции сохрани `feedback` с источником, предметом, областью и действием.
Сначала найди конкретный элемент по файлу или фрагменту пользователя. Затем определи,
какие применения входят в правку и какие остаются прежними. В отчёте достаточно
короткой записи: требование → затронутые файлы → выполненная проверка. Проверяй весь
заказанный набор, включая обложку, гайд, галерею и ZIP, если они содержат этот элемент.
При неопределённой области выполни очевидную локальную правку; общее правило оставь
предложением, не объявляй глобальный запрет.

Новую версию собирай из актуального списка сдаваемых файлов. Сверь, что отклонённые
применения не вернулись из старых экспортов или генератора. Сами исторические версии
сохраняются. QA относится к новым байтам; неизменные активы можно сверить по хешу,
не приписывая им повторный визуальный просмотр.

## Граф и дальнейшее применение

В существующем графе — обычный `artifact`, `data.kind: visual-profile`, дополнительно
`artifactKind: brand-identity`, `productId`, `segmentIds`, `version`, `decision`,
`decisionSource` при accepted, `readiness`, `profileFile` на identity.json. **Без channelId:**
это система бренда. `source` — путь единственного отчёта без fragment. `supersedes` —
только предыдущая brand-identity того же продукта; basedOn указывает предыдущую
версию identity.json, прочие входы сохраняются в sources. Не заменять произвольный product-level visual-profile только
потому, что у него тоже нет channelId. Узел остаётся hypothesis: одобрение дизайна не
повышает его рыночный статус.

Операции writer по GRAPH-WRITES: `node` профиля, при необходимости выбранный `move`,
и `complete` для точного запуска. Сначала файлы и validate.cjs, затем dry run пакета
с expectedRevision и применение. При конфликте перечитай ревизию, не перетирай. Без
графа можно сдать файлы с product.id=null; не создавать второй PRODUCT.md или
выдуманные сегменты. Если регистрацию просили, а runtime недоступен, назови её пробелом.

Для оформления отдельного канала или отдельного поста: передай принятую
brand-identity и её
artifactId/version как основание, а каналу — собственную адаптацию и ограничения;
канал берёт из бренда аватар, иконку, тёмную тему и og-image как готовые файлы
(`files` с `purpose`), а не перерисовывает их.
В профиле канала можно хранить `brandIdentityArtifactId` и `brandIdentityVersion`.
Это зависимость, не supersedes: адаптация канала не отменяет бренд. Применяющий агент
сохраняет required-правила бренда, а локальные изменения не повышает до общего ребрендинга.

Короткий итог в чате содержит основные изображения, ссылки на файлы, выполненный объём,
выбор/статус и оставшиеся вопросы. Не отдавать только JSON или план будущего производства.
